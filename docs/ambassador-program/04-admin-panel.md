# Амбассадорская программа — Административная панель и логика распределения

Версия: 1.0 (MVP). Реализация — по образцу существующей `admin-analytics.html`:
статические страницы в `public/` + JSON API `/api/amb/*` с проверкой роли в сессии.

Доступ: аккаунты сайта (`users`) с программной ролью. Каждый видит только свою
ветку: тимлид — команду, координатор — поток, head (Алиби) и техадмин — всё.

## Страницы

### 1. `amb-admin.html` — Дашборд

Верхняя строка — карточки-показатели (для head по всей программе,
для координатора/тимлида автоматически сужается до их ветки):

| Блок | Показатели |
|---|---|
| Воронка набора | заявок всего / за неделю · на рассмотрении · принято · конверсия |
| Состав | всего участников · по ступеням лестницы · активные / неактивные |
| Потоки | 4 колонки: людей, команд, % сдачи отчетов, средние баллы |
| Треки | распределение по 11 направлениям (основное/дополнительные) |
| Задания | открытых · отчетов на проверке (⚠ если > 10) · просрочено |
| Отчетность | % сдавших еженедельный отчет (эта неделя / прошлая) · needs_help |
| Источники | регистрации по source (site/wa/inst/friend) и их конверсия |
| Тревоги | unresponsive · needs_support · заявки старше 7 дней без решения |

### 2. `amb-applications.html` — Заявки

- Очередь с фильтрами: статус, вид (новая/миграция), трек, город, возраст,
  дата подачи. Сортировка по давности — старые сверху.
- Карточка кандидата: анкета целиком, выбранные треки, мотивация,
  **вводное задание** (текст — инлайн; видео — кнопка «Открыть в Telegram»,
  бот пересылает файл админу по file_id), источник, флаг is_minor.
- Поле внутренних комментариев (не видно кандидату).
- Действия: [Принять] [В резерв] [Отклонить] [На доработку] [На интервью] —
  каждое с полем причины; решение автоматически уходит кандидату в бот.
- Массовые действия для миграционных заявок (принять пачкой).

### 3. `amb-people.html` — Участники

- Таблица: KYD-номер, имя, ступень, статус активности, поток, команда,
  тимлид, баллы, последний отчет, город, треки. Фильтры по всем колонкам,
  поиск, экспорт CSV (только head/координатор).
- Профиль участника: все данные + история баллов (ledger) + история статусов +
  выполненные задания + посещенные мероприятия + отчеты.
- Действия (по правам): сменить статус активности, перевести в другую
  команду/поток, начислить/списать баллы (причина обязательна),
  рекомендовать на повышение / повысить (head), написать в бот участнику.

### 4. `amb-tasks.html` — Задания

- Список заданий (свои + вниз по ветке), статусы, счетчики взявших/сдавших.
- Форма создания: все поля из `amb_tasks` + выбор аудитории
  (все / поток / команда / трек).
- **Очередь проверки:** отчеты со статусом submitted → просмотр контента →
  [Принять +N баллов (слайдер в диапазоне min–max)] / [Отклонить + причина].
  Принятие пишет в ledger и уведомляет участника одной транзакцией.

### 5. `amb-events.html` — Мероприятия

- CRUD мероприятий, список зарегистрированных, отметка посещения вручную.
- Кнопка «QR для входа» — генерирует PNG с `t.me/<bot>?start=ev_<token>`
  (QR рисуется на клиенте, библиотека qrcode — 1 файл в vendor/).

### 6. `amb-reports.html` — Еженедельные отчеты

- Сводка по команде/потоку за выбранную неделю: кто сдал / не сдал,
  ответы, флаги needs_help (сверху, красным).
- Кнопка «Напомнить несдавшим» (шлет через бот, не чаще 1 раза в день).

## Логика распределения по потокам и командам

В MVP распределение **ручное с подсказками** (автораспределение — v2).

### Правила

1. Кандидат принят → попадает в пул «нераспределенные» на дашборде.
2. Панель показывает загрузку: люди/вместимость каждой команды и потока.
3. Рекомендация системы (подсветка): **наименее загруженная команда
   наименее загруженного потока**, вместимость команды по умолчанию 20.
4. Разумные эвристики при ручном выборе (панель показывает, но не принуждает):
   - города-миллионники можно распределять равномерно, регионы — не дробить
     поодиночке (человеку комфортнее с земляками);
   - несовершеннолетних — к опытным тимлидам;
   - primary-трек участника ≠ критерий команды (команды — управленческие,
     не тематические) — это принципиально по концепции.
5. Перевод между командами/потоками — только координатор+ с причиной,
   пишется в `amb_status_history`.
6. Тимлид назначается из участников ступени senior+ (head выбирает);
   при назначении `program_role='teamlead'` и `amb_teams.teamlead_id`
   обновляются одной транзакцией. Аналогично координатор.

### Первичное распределение миграционной волны

370 человек за раз вручную — тяжело. Порядок:

1. Сначала head назначает 4 координаторов и ~20 тимлидов из проверенных людей
   (создаются потоки и команды).
2. Прошедшие верификацию копятся в пуле; раз в несколько дней head/координаторы
   распределяют пачкой (мультивыбор → «в команду X»).
3. Балансировка по городам/часовым поясам — по эвристикам выше.

## API (сводно, детали в ТЗ)

```
GET  /api/amb/dashboard            — метрики (сужение по роли)
GET  /api/amb/applications?filters — очередь заявок
POST /api/amb/applications/:id/decision   {action, reason}
GET  /api/amb/people?filters
GET  /api/amb/people/:id           — полный профиль + истории
POST /api/amb/people/:id/status    {field, value, reason}
POST /api/amb/people/:id/assign    {stream_id, team_id, reason}
POST /api/amb/people/:id/points    {delta, reason}
CRUD /api/amb/tasks, /api/amb/events
GET  /api/amb/review-queue         — отчеты на проверке
POST /api/amb/assignments/:id/review {action, points, comment}
GET  /api/amb/weekly?week&team
POST /api/amb/notify               — сообщение участнику/сегменту через бот
```

Каждый endpoint проверяет: (а) роль, (б) принадлежность объекта ветке
запрашивающего. Проверка ветки — одна общая функция `canAccessProfile(admin, profile)`.
